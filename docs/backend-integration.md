# Интеграция с бэкендом

В `.env.local` (или `.env`) задайте `NEXT_PUBLIC_API_URL`. Корневой URL, например `https://backend.example`, используется со стандартным префиксом `/api/v1`. Можно указать URL сразу с префиксом. Серверный `API_URL` при необходимости переопределяет адрес для прокси; для включения серверного интерфейса оставьте заданным `NEXT_PUBLIC_API_URL`. Пример переменных — в `.env.example`.

`NEXT_PUBLIC_API_URL` встраивается в клиентскую сборку, а прокси читает `API_URL` или `NEXT_PUBLIC_API_URL` в рантайме. В production `NEXT_PUBLIC_API_URL` обязателен на обоих уровнях: иначе клиент выберет локальный режим или прокси вернёт 502; `API_URL` — необязательный runtime-override. `docker-compose.prod.yml` и deploy-job передают значения в контейнер, требуют `NEXT_PUBLIC_API_URL` и проверяют `/api/backend/health` после выката.

Браузер обращается к `/api/backend` своего Next.js сервера. Прокси обращается к бэкенду, хранит токены в HttpOnly cookie, автоматически обновляет сессию после 401 и не возвращает токены клиентскому коду. В production необходим HTTPS. Приложение требует сервер Next.js; статического хостинга недостаточно.

## Подключённые сценарии

- Регистрация, вход с паролем, восстановление сессии, выход и чтение профиля.
- Список, создание, изменение и удаление путешествий, включая название, описание, даты и ссылку на обложку.
- Чтение и CRUD точек, событий и перемещений; ссылки бронирования и привязка событий к точкам.
- Совместный доступ: создание кода-приглашения, присоединение по коду и список участников поездки. Используются `POST /trips/{trip_id}/code/generate`, `POST /trips/code/redeem/{code}` и `GET /trips/{trip_id}/collaboratrs`; прокси пропускает эти пути.
- Удаление точки с удалением связанных перемещений и сохранением событий без места; удаление содержимого перед удалением поездки. Эти операции состоят из нескольких запросов: при сбое уже выполненные удаления не откатываются, а интерфейс перечитывает состояние сервера.

Идентификаторы бэкенда превышают `Number.MAX_SAFE_INTEGER`. Адаптер сохраняет их строками и передаёт десятичные строки даже там, где OpenAPI описывает число. Приём таких значений проверен на работающем API. Единственное приведение типа в `apiId` нужно для несовпадения сгенерированных типов с фактическим int64-контрактом.

События и перемещения требуют времени со смещением: адаптер добавляет `:00Z` и сохраняет цифры часов, а не пересчитывает их по часовому поясу браузера. При чтении время возвращается в локальный формат `YYYY-MM-DDTHH:mm`. Модель часовых поясов отдельных городов пока отсутствует.

## Ограничения текущего API

В схеме нет изменения имени пользователя, загрузки файлов и метаданных материалов, удаления участника поездки и изменения описания существующего перемещения. Смена пароля доступна через `PUT /auth/me/password`. Соответствующие поля интерфейса показывают ограничение. Сервер принимает HTTP(S)-ссылку на обложку и файл через `PUT /trips/{trip_id}/cover`; локальный режим сохраняет загрузку картинки.

Фотографии и документы остаются в IndexedDB этого браузера. Метаданные материалов и выбор активной поездки хранятся в отдельном пространстве `travelhub.remote.<userId>`. Они восстанавливаются после повторного входа в этом браузере, но не синхронизируются между устройствами. Старые локальные аккаунты и поездки сохраняются и не мигрируют автоматически.

SDK обновлён генератором по полученной OpenAPI-схеме. `npm run openapi` загружает свежую схему с настроенного бэкенда. Локальный снимок `openapi.json` не коммитится; для генерации без сети положите его в корень проекта и выполните `npx.cmd openapi-ts --input ./openapi.json`.

## Проверка

Обычные проверки: `npm run lint`, `npm test`, `npm run build`.

Для проверки реального API запустите `npm run dev -- --port 3001`, затем `npm run test:backend`. Другой адрес приложения задаётся через `TEST_APP_URL`. Скрипт создаёт временные тестовые данные, проверяет авторизацию, CRUD всех сущностей, обложку по ссылке, создание кода приглашения, список участников, обновление токена и выход, затем удаляет свои записи и аккаунт. Тесты Vitest дополнительно проверяют отказы API, частичное удаление, точность идентификаторов, недоступность токенов клиентскому коду и соответствие всех неадминских методов сгенерированного SDK allowlist прокси.

Во время первого прогона вложенных сущностей обнаружилось, что сервер запрещает удалять непустую поездку. До исправления очистки на бэкенде остались тестовая поездка `1568610886538672011` с двумя точками и событием и её временный аккаунт. Пароль был случайным и не сохранялся, поэтому удалить эти записи теперь сможет администратор бэкенда. Все последующие прогоны очистили свои данные успешно.
